Redesign and extend the existing Corporate Actions Impact Copilot UI so the complete end-to-end operational flow is obvious, usable and demonstrable.

First inspect the existing application, API, data model and the two recently added demo-requirement documents under `attached_assets/Pasted-*.txt`.

Preserve useful existing functionality. Do not rebuild working components without reason. Extend the current application into a coherent operations workbench.

This task is primarily about product flow and UI behaviour, but update the API and data model wherever required to make every interaction functional and persistent.

CORE UX DECISION

The application should have three levels:

1. Operations Dashboard — what requires attention?
2. Event Inbox — what corporate-action cases exist?
3. Event Workbench — what must I do next for this particular case?

Do not make every workflow stage a separate top-level navigation item. The corporate-action lifecycle should live inside the Event Workbench.

The user must always understand:

- What event am I viewing?
- What stage is it at?
- What has already been completed?
- What is blocking progress?
- What is the next action?
- What is the deadline?
- Who owns the next action?
- Where did each material value come from?

WORKFLOW STEPPER

1. Notice
2. Review Terms
3. Eligibility

5. Election

7. Instruction

9. Close

Each stage needs one of these states:

Clicking a completed stage should allow the user to review it. Clicking a future blocked stage should explain what must happen first.

Do not allow invalid workflow jumps.

IMPORTANT INTERACTION RULES

Every primary button must do something real and persist the result.

Examples:

- Accepting a field changes its review state.
- Editing a field requires a reason and writes an audit record.
- Validating terms changes the event status.
- Confirming eligibility persists the eligible positions.
- Running calculation creates a calculation version.
- Submitting an election changes its status.
- Approval records the checker.
- Simulated send creates an instruction record.
- Settlement comparison creates a reconciliation result.
- Closing an event requires all blocking controls to pass.

Use clear success and error messages.

When an action is blocked, explain exactly why:

“Cannot calculate impact: subscription price has not been validated.”

Do not merely disable buttons without explanation.

DEFINITION OF DONE

The UI redesign is complete only when:

1. A user can upload the sample rights-issue notice.
2. The user can review extracted terms beside source evidence.
3. The user can validate the terms.
4. The system identifies eligible holdings.
5. The system calculates entitlements and funding.

8. The system generates a simulated instruction.
9. Settlement data produces one match and one break.

11. The event can be closed only after required controls pass.
12. Every action appears in the audit history.
13. A cash-dividend event correctly skips the election stage.
14. Refreshing the application does not lose workflow progress.
15. No primary action is a non-functional placeholder.
