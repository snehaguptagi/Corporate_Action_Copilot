Build a full-fledged, working POC called “Corporate Actions Impact Copilot.”

This is an internal operations tool for fund operations, custody operations and risk-management teams. It is not a customer-facing investment application.

The POC must demonstrate how a corporate-action notice moves from an unstructured document to a reviewed, calculated, approved and auditable operational case.

Use the existing codebase where possible. Inspect what is already working before changing anything. Do not create disconnected screens or placeholder buttons. Every page, status, calculation and button must fit into one consistent end-to-end workflow.

PRODUCT OBJECTIVE

Corporate-action notices arrive as PDFs, emails or custodian messages. Analysts must manually read them, understand the event, find affected holdings, calculate the impact, manage deadlines and elections, create downstream tasks, send instructions, reconcile settlement and retain evidence.

The Copilot should reduce this manual effort while keeping an analyst in control.

The application should:

1. Read and classify a corporate-action notice.
2. Extract important event terms with evidence.
3. Let an analyst validate or correct those terms.
4. Identify affected funds, accounts and positions.
5. Calculate the expected cash or security impact.
6. Manage elections only when the event requires a choice.
7. Generate an operational checklist and downstream tasks.
8. Support maker-checker approval.
9. Simulate an instruction without sending anything externally.
10. Reconcile the expected result against the actual settlement.
11. Maintain a complete audit trail.

IMPORTANT PRODUCT PRINCIPLES

The AI may read, classify, extract, summarise and suggest.

Deterministic application logic must perform financial calculations, deadline rules, validations and workflow transitions.

The AI must never silently invent a missing rate, ratio, date, currency, option or holding. Missing or conflicting information must be clearly flagged for analyst review.

The system must never automatically submit a market instruction or make an investor election. All external instructions in the POC must be labelled “DRAFT” or “SIMULATED.”

CORE USER ROLES

1. Operations Analyst — reviews notices, validates extracted fields, checks impacts and prepares elections or instructions.
2. Reviewer/Checker — independently reviews and approves controlled actions.
3. Operations Manager — monitors deadlines, high-risk cases, overdue tasks and reconciliation breaks.

For the POC, provide a simple role switcher so these workflows can be demonstrated without building full authentication.

SUPPORTED EVENT TYPES

Design the system so new event types can be added later. The POC should contain working scenarios for:

- Cash dividend
- Stock dividend or bonus issue
- Stock split or reverse split
- Rights issue
- Tender offer
- Merger or acquisition with cash, shares or mixed consideration

Each event must be marked as:

- Mandatory — processed automatically according to the announced terms.
- Voluntary — the holder must choose an option.
- Mandatory with options — the event will proceed, but the holder may select from available options.

Do not show an election workflow for a normal mandatory event.

END-TO-END WORKFLOW

Stage 1: Notice intake

Allow the analyst to upload a corporate-action PDF. Include seeded sample notices so the demo works immediately.

Create an event case with:

- Internal event ID
- Source or custodian reference
- Notice filename
- Receipt date and time
- Issuer
- Security name
- ISIN or other security identifier
- Current processing status

Stage 2: Notice analysis

Extract and display:

- Event type
- Mandatory or voluntary classification
- Issuer and affected security
- Announcement date
- Ex-date
- Record date
- Payment or settlement date
- Market deadline
- Internal operational deadline
- Currency
- Cash rate, exchange ratio or entitlement ratio
- Available options
- Default option
- Subscription or offer price
- Restrictions and important conditions

Every extracted value must show:

- Source page
- Supporting text snippet
- Confidence level
- Review status
- Whether the value was AI-extracted or manually corrected

Allow the analyst to accept, edit or reject each field. Record every correction in the audit trail.

Calculations must remain blocked until the required fields for that event type are validated.

Stage 3: Eligibility and affected positions

Use synthetic holdings data containing funds, custody accounts, security identifiers, quantities and position dates.

Match the validated event security against the holdings and identify affected positions.

Do not simply use today’s holding. Show which position date is being used for eligibility and why.

Display:

- Fund
- Account
- Eligible quantity
- Position date
- Matching security identifier
- Eligibility status
- Any data-quality warning

Stage 4: Impact calculation

Create a deterministic calculation engine. Each result must show inputs, formula, output, currency, rounding and assumptions.

Examples:

- Cash dividend: eligible quantity × dividend rate
- Stock split: eligible quantity × split factor
- Rights issue entitlement: eligible quantity × entitlement ratio
- Rights subscription cost: elected rights × subscription price
- Tender consideration: elected quantity × offer price
- Mixed merger: eligible quantity × cash rate plus eligible quantity × share-exchange ratio

Handle fractional entitlements explicitly. Show whether fractions are rounded, carried, ignored or paid in cash. Never hide the assumption.

Allow the analyst to rerun the calculation after correcting a validated input. Recalculation must create an audit entry.

Show totals by:

- Event
- Fund
- Account
- Currency
- Cash or security movement

Stage 5: Elections

Use the word “election” only when a corporate action gives the holder a choice.

For voluntary or mandatory-with-options events, show:

- Available election options
- Default option
- Eligible quantity
- Quantity allocated to each option
- Market deadline
- Earlier internal deadline
- Required cash funding
- Supporting notice evidence
- Analyst comments

Validate that elected quantities do not exceed the eligible quantity.

The Copilot may explain the options and highlight operational consequences, but it must not choose an investment option automatically.

Require maker-checker approval before the election can move to “Approved.”

Stage 6: Downstream task generation

Generate a task checklist based on the event type and validated terms.

Possible tasks include:

- Validate notice terms
- Confirm eligible positions
- Review tax or market restrictions
- Confirm cash funding
- Obtain election decision
- Complete maker-checker approval
- Prepare custodian instruction
- Monitor acknowledgement
- Check cash receipt
- Check security receipt
- Investigate settlement difference
- Close the event

Every task should have an owner, due date, priority, status and event reference.

Calculate task deadlines from the validated market deadline and a configurable internal buffer. Clearly distinguish market deadline from internal deadline.

Stage 7: Instruction simulation

Generate a structured draft instruction containing the event reference, account, security, option, quantity, deadline and approval details.

The POC must not send instructions externally.

Allow the analyst to click “Simulate Send.” Change the status to “SIMULATED — NOT SENT” and create an audit entry.

Stage 8: Settlement reconciliation

Allow seeded or manually entered settlement results.

Compare expected and actual:

- Cash amount
- Currency
- Security quantity
- Settlement date
- Account

Classify the result as:

- Matched
- Partially matched
- Missing
- Over-settled
- Under-settled
- Wrong currency
- Wrong account

Create an exception task when a difference is found. Show the expected value, actual value, difference and suggested investigation steps.

Stage 9: Audit trail

Maintain a chronological, append-only event history showing:

- Timestamp
- User or system actor
- Action
- Old value
- New value
- Reason or comment
- Related evidence
- Workflow status

The audit trail must include extraction, manual corrections, calculations, elections, approvals, simulated instructions, reconciliation and closure.

APPLICATION SCREENS

1. Operations Dashboard

Show:

- Active events
- Events approaching deadline
- High-risk cases
- Elections awaiting action
- Open tasks
- Reconciliation breaks
- Traffic-light risk status: red, amber or green

2. Event Inbox

Provide searchable and filterable events by type, classification, status, market, deadline and risk.

3. Notice Intake and Review

Upload a notice and review the extracted fields beside the supporting source evidence.

4. Event Workbench

Use tabs or clear sections for:

- Overview
- Source Evidence
- Affected Positions
- Impact Calculation
- Elections
- Tasks
- Instruction
- Reconciliation
- Audit History

5. Tasks and Risk

Show overdue, due-today and high-priority operational tasks across all events.

6. Audit Trail

Provide a searchable cross-event operational history.

STATUS MODEL

Use a controlled status flow:

Received → Extracted → Under Review → Validated → Impact Calculated → Election Required or Instruction Ready → Awaiting Approval → Approved → Simulated Instruction → Awaiting Settlement → Reconciled or Break Identified → Closed

Mandatory events must bypass “Election Required.”

Do not allow invalid status jumps. Display why a blocked action cannot continue.

DEMO DATA

Seed at least six realistic cases:

1. Mandatory cash dividend needing source review.
2. Mandatory stock split ready for settlement.
3. Voluntary rights issue requiring an election.
4. Voluntary tender offer awaiting approval.
5. Mixed-consideration merger with a fractional entitlement.
6. Settled event containing a reconciliation break.

Use entirely synthetic companies, securities, accounts and funds. Clearly label the environment as “POC — Synthetic Data.”

TECHNICAL APPROACH

Use:

- React, Vite and TypeScript for the frontend
- Tailwind CSS and accessible reusable components
- Node.js and Express for the API
- PostgreSQL with Drizzle ORM
- Zod for request and response validation
- OpenAPI as the API contract
- React Query for API state
- PDF text extraction, with an OCR fallback for scanned documents
- A document-retrieval layer for finding source snippets in notices and optional SOP documents

“RAG” in the AI architecture means Retrieval-Augmented Generation: retrieve relevant notice or SOP passages and provide them to the model. Do not confuse it with the red-amber-green operational risk indicator.

For AI extraction, create a structured schema and return values, confidence, source page and source text. If no model API key is present, the entire demo must still work through deterministic seeded extraction results.

POC GUARDRAILS

- Synthetic information only
- No real customer data
- No real custodian connectivity
- No real market instruction
- No autonomous investment decision
- Human approval for controlled actions
- Evidence visible beside AI output
- Deterministic financial calculations
- Complete audit trail
- Clear “DRAFT,” “SIMULATED” and “POC” labels

QUALITY REQUIREMENTS

- All buttons and navigation must work.
- Data must persist after page refresh.
- No disconnected mock screens.
- No calculation values hardcoded directly into UI components.
- The same event data must drive the dashboard, workbench, tasks and audit history.
- Empty, loading, error and validation states must be designed.
- Use realistic but readable operational language.
- Explain specialised terms through tooltips.
- Keep the design professional and suitable for an institutional operations team.
- Do not make it look like a retail trading platform.
- Add calculation unit tests and API workflow tests.
- Include a README with setup, environment variables, database setup, demo users and run commands.
- Provide one command that starts the complete local development application.

ACCEPTANCE SCENARIOS

The POC is complete only when these work:

1. An analyst opens a cash-dividend notice, validates extracted fields and calculates impacts without seeing an election step.
2. An analyst opens a rights issue, reviews options, enters an election and sends it for checker approval.
3. A checker approves the election and a simulated instruction is created.
4. Editing a validated rate recalculates the impact and produces an audit entry.
5. A missing required term blocks calculation and explains what must be fixed.
6. A settlement difference creates a reconciliation break and investigation task.
7. Every extracted term can be traced to source evidence.
8. Every controlled action appears in the audit trail.
9. The seeded demo works without an external AI API key.
10. The full workflow can be demonstrated from notice intake to case closure.

Start by reviewing the existing application and data model. Preserve useful working features, fix inconsistencies and implement the missing workflow. Build and test the complete POC rather than only generating a design or project scaffold.
